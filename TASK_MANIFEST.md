## Repo topology (decided)

Three repos under `fendix-services/`:

| Repo | Path | Role in v0.20 |
|------|------|---------------|
| **fendix-engine** | `Fendix/` (this repo, `github.com/Abdel-RahmanSaied/Fendix`) | **All v0.20 work happens here** |
| fendix-backend | `fendix-backend/` (Django) | Holds the roadmap docs only — no v0.20 code |
| fendix-frontend | `fendix_frontend/` (Next.js) | **Out of scope** — metrics dashboard is standalone static HTML, no FE build |

**Decisions locked (operator-confirmed 2026-06-28):**
1. Work in the **engine repo**; manifest + phase docs live at `Fendix/` root.
2. Go module is rooted at `go/` → **all Go code goes under `go/...`**; Go tests stay in-module under `go/tests/`. Non-Go artifacts (`benchmarks/`, `metrics/`, `tools/`) sit at engine root.
3. Benchmark/metrics exposed as **`fendix` subcommands** (`fendix benchmark`, `fendix metrics`) — NOT a separate `cmd/benchmark` binary.
4. **Docker is available** → DVWA/Juice Shop targets run against real containers; OWASP Benchmark downloads its corpus.

## Ambiguities

**BLOCKER #1 — RESOLVED 2026-06-28 → Option (B) Parallel framework** *(operator decision)*. Build the new Go benchmark framework as the agent file specifies. Orchestrator guardrail to keep it Rule-1-safe: the new framework is **strictly additive** — new CI workflow is named `baseline.yml` (NOT a rewrite of `benchmark.yml`), and the existing `scripts/` harness + `ci.yml` are left untouched. A5/B1/B3 unblocked.

*(original options retained for the record)* How does the new Go benchmark framework relate to the existing shell/Python harness?
- **(A) Consolidate / wrap (recommended, Rule-1-compliant):** Go `internal/benchmark` + `baseline.json` + `fendix benchmark` become a thin orchestration/normalization layer that **invokes and ingests** the existing `run-juice-shop.sh` / `heavy-eval` / `fp-corpus` outputs, adds delta-regression, and emits one committed `baseline.json`. Minimal duplication. New CI = `baseline.yml` (delta gate) sitting beside the existing absolute-threshold gates.
- **(B) Parallel framework (agent file literal):** New Go targets re-run scans independently of the shell harness. Faster to write in isolation but creates two competing benchmark systems → drift, Rule 1/10 violation.
- **(C) Formalize-only (lightest):** No Go framework; generate `baseline.json` from existing numbers + add only the metrics collector/dashboard + a small compare script.

**Resolved by operator answers:** repo target, CLI shape (subcommands), Docker availability.

**BLOCKER #2 — OWASP Benchmark vs the Java timeline (roadmap inconsistency).** v0.20 and v0.26 both list **OWASP Benchmark** as a target, but it is a **Java** application and Fendix has **no Java analyzer until v0.27**. Running it now yields recall ≈ 0 — a misleading baseline, not a real one (violates Rule 5). **Decision taken:** the OWASP target loudly **SKIPS** with that reason; the real v0.20 DAST baseline is DVWA + Juice Shop (language-agnostic HTTP probing). **Action for the roadmap owner:** either (a) move OWASP Benchmark from v0.20/v0.26 to v0.27+ (after Java), or (b) swap in a language-appropriate SAST corpus for v0.20 (the existing `scripts/heavy-eval` Juliet-style corpus already covers Python/Go SAST and could be wrapped as a 4th target). Recommend (a)+(b).

**Minor (Architect's discretion, documented):**
- Benchmark/metrics data dirs are CWD-relative; add `--baseline-dir`/`--metrics-dir` overrides + document "run from engine root."
- `make` targets (`bench`, `benchmark`, `heavy-eval`) should gain a wrapper to the new `fendix benchmark` once it exists, or stay as-is and be called by it.
